# AI Requirements Reviewer

## Быстрый запуск для проверки

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Откройте .env и вставьте свой LLM_API_KEY (OpenRouter)
python agent.py --input docs/requirements.md --output report.md
```

`docs/requirements.md` — путь к проверяемому ТЗ; для документа организаторов
используйте `documents_organization/requirements.md`. Отчёт появится по пути,
указанному в `--output`; недостающие каталоги создаются автоматически.

ИИ-агент для статической проверки документов с требованиями: извлекает
отдельные требования, проверяет качество каждого из них по критериям
ISO/IEC/IEEE 29148 и IEEE Std 830 и сохраняет структурированные результаты.

Проект для **BCC-HUB x MNU FinTech Hackathon**. Входной документ
организаторов лежит в `documents_organization/requirements.md` (файл не
коммитится — сдаётся отдельно вместе с отчётом).

## Текущий статус

Реализована интеграция с реальной LLM через OpenAI-совместимый API:

- загрузка Markdown и PDF (PyMuPDF, с номерами страниц);
- нарезка документа на чанки с перекрытием и сохранением разделов;
- две модели по этапам: быстрая (`EXTRACTOR_MODEL`) извлекает требования и
  делает дешёвый triage, тяжёлая (`AUDITOR_MODEL`) проводит глубокие проверки;
- LLM-извлечение требований с валидацией ответа через Pydantic;
- статический линтер до аудита: пустые шаблоны, заглушки, незаполненные
  ячейки, нечёткие слова и противоречия HTTP-кодов/методов;
- каскадная проверка: Haiku с `effort=low` отправляет на дорогой аудит только
  подозрительные требования, остальные остаются PASS;
- entity-based кластеризация требований: связанные пункты (эндпоинты, поля,
  суммы, единицы `тиын`/`тенге`) попадают в один пакет до 20 штук;
- prefix caching: у всех запросов аудитора одинаковый системный префикс
  `[auditor_system] + [полный документ]`, а пакет и задача идут в конце;
- причинный порядок JSON: `evidence -> explanation/description -> criterion/
  category -> severity`, поэтому `AUDITOR_EFFORT=medium` достаточно;
- fuzzy-сверка evidence через `difflib` с порогом 92%: цитата заменяется
  точным фрагментом исходника, повтор LLM нужен только при реальной галлюцинации;
- проверка всего набора: нестыковки разделов, противоречия, дубликаты,
  пропуски, заглушки и покрытие целей документа;
- детерминированный вердикт READY / NEEDS_REVISION / BLOCKED с планом
  первоочередных исправлений;
- сохранение промежуточных результатов в JSON;
- Markdown-отчёт с нарезкой, флагами линтера, находками, аудитом набора и итогом;
- понятные ошибки и ненулевой exit code при недоступности API.

## Установка

Требуется Python 3.11+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Ключ LLM (OpenRouter)

Проект использует пакет `openai` и любой OpenAI-совместимый endpoint.
Для OpenRouter:

1. Зарегистрируйтесь на <https://openrouter.ai/>.
2. Откройте <https://openrouter.ai/keys> и создайте ключ.
3. Скопируйте пример конфигурации и заполните `.env`:

   ```bash
   cp .env.example .env
   ```

   ```dotenv
   LLM_API_KEY=sk-or-v1-ваш-ключ
   LLM_BASE_URL=https://openrouter.ai/api/v1
   LLM_MODEL=anthropic/claude-haiku-5.5
   # Модели по этапам (без них используется LLM_MODEL):
   EXTRACTOR_MODEL=anthropic/claude-haiku-5.5
   AUDITOR_MODEL=meta/muse-ember
   # Режим рассуждений:
   EXTRACTOR_EFFORT=low
   AUDITOR_EFFORT=medium
   ```

4. Выберите модель в каталоге <https://openrouter.ai/models>. Модель должна
   поддерживать JSON output (`response_format: json_object`); если провайдер
   его не поддерживает, клиент автоматически повторит запрос без этого
   параметра и разберёт JSON безопасным парсером.

### Модели этапов и режим рассуждений

Извлечение и triage идут моделью `anthropic/claude-haiku-5.5` с
`reasoning.effort = low`. Глубокую проверку требований и всего набора ведёт
`meta/muse-ember` с `reasoning.effort = medium`: причинный порядок полей JSON
заставляет модель сначала цитировать и анализировать, а уже потом ставить
severity, поэтому `max` больше не нужен. Оба слоуга есть в каталоге
OpenRouter и объявляют параметр `reasoning`.

Обе настройки называются `..._EFFORT` и уходят в одном формате:
`reasoning: {"effort": ..., "exclude": true}` через `extra_body` клиента
`openai`. Поле `exclude` убирает thinking-трейс из ответа, но токены всё
равно тарифицируются как output. Нельзя одновременно слать `reasoning_effort`
и `reasoning.effort` с разными значениями — OpenRouter вернёт 400, поэтому
используется только unified-форма.

Допустимые уровни различаются по моделям и проверяются при загрузке `.env`:

| Модель | Доступные `effort` |
| :--- | :--- |
| `anthropic/claude-haiku-5.5` | `none`, `low`, `medium`, `high`, `xhigh`, `max` |
| `meta/muse-ember` | `minimal`, `low`, `medium`, `high`, `xhigh`, `max` |

`none` для Muse Ember приведёт к 400: модель всегда думает. Режимы этапов
попадают в паспорт прогона. Клиент не отправляет `temperature` — Haiku 5.5
отвергает любое значение, кроме `1`. Ограничений `max_tokens` нет: ответ
ограничен только лимитом самого провайдера.

`.env` уже добавлен в `.gitignore`. Ключ никогда не выводится в логах,
отчёте или сообщениях об ошибках.

### Переменные окружения

| Переменная | Обязательна | Значение по умолчанию | Назначение |
| :--- | :--- | :--- | :--- |
| `LLM_API_KEY` | да | — | API-ключ провайдера |
| `LLM_BASE_URL` | нет | `https://openrouter.ai/api/v1` | OpenAI-совместимый endpoint |
| `LLM_MODEL` | нет, если заданы модели этапов | — | Модель по умолчанию |

| `EXTRACTOR_EFFORT` | нет | `low` | `reasoning.effort` для извлечения |

## Запуск

Основной способ — корневой `agent.py`, без подкоманд:

```bash
python agent.py \
  --input documents_organization/requirements.md \
  --output reports/report.md
```

Или напрямую через venv:

```bash
.venv/bin/python agent.py \
  --input documents_organization/requirements.md \
  --output reports/report.md
```

Для обратной совместимости остаётся и старый вызов с подкомандой `analyze`:

```bash
python -m app.main analyze \
  --input documents_organization/requirements.md \
  --output reports/report.md
```

Поддерживаются `.md`, `.markdown` и `.pdf`.

Что появится после успешного прогона:

- `reports/report.md` — отчёт с нарезкой, проверкой каждого требования,
  аудитом всего набора, сводкой и итоговым вердиктом;
- `reports/report.requirements.json` — извлечённые требования, ID, категории,
  исходные ID, местоположение и паспорт прогона (включая коммит агента);
- `reports/report.analysis.json` — находки по каждому требованию, статусы,
  severity, аудит набора и вердикт.

В старом CLI промежуточные JSON можно отключить флагом `--no-save-json`.

Если ключ не задан, API недоступен, закончилась квота или ответ модели
невалиден, команда печатает понятную ошибку и завершается с кодом `1`.
Фальшивый «успешный» отчёт при этом не создаётся. Если извлечение уже
успело завершиться, его JSON сохраняется для диагностики.

## Как это работает

1. `DocumentLoader` читает Markdown или PDF.
2. `DocumentChunker` режет документ по заголовкам и абзацам на чанки с
   перекрытием, не разрывая строки и сохраняя путь разделов/номер страницы.
3. `RequirementExtractor` отправляет каждый чанк в LLM с промптом
   `app/prompts/extract_requirements.txt`. Модель возвращает JSON, который
   валидируется Pydantic. Дубликаты из перекрывающихся чанков схлопываются,
   внутренние ID `REQ-001…` присваиваются приложением, исходные ID
   (`Ф-1`, `REQ-12`) сохраняются.
4. `StaticLinter` детерминированно ищет дефекты, которые не требуют LLM:
   пустые шаблоны (`Да / Нет`), заглушки («заполняются тестировщиками»),
   незаполненные ячейки и прочерки, нечёткие слова («быстро», «удобно»,
   «при необходимости») и несоответствия HTTP-кодов/методов. Флаги
   передаются аудитору как `pre_detected_flags`; подтверждённые флаги
   попадают в отчёт, даже если модель о них промолчала.
5. `RequirementTriage` (Haiku, `effort=low`) делает быстрый проход по всем
   требованиям и отмечает только те, где есть конкретный риск. Требования
   с флагами линтера отправляются на глубокую проверку всегда. Если triage
   недоступен или вернул мусор, безопасный fallback проверяет весь набор.
6. `RequirementAnalyzer` (Ember, `effort=medium`) группирует подозрительные
   требования по сущностям: общий эндпоинт, поле БД, сумма, единица
   измерения или редкий термин удерживают связанные пункты в одном пакете
   до 20 штук. Полный текст документа лежит в неизменном системном
   префиксе, поэтому провайдер может переиспользовать prefix cache.
7. Каждая цитата evidence нормализуется и fuzzy-сверяется с документом
   (`difflib.SequenceMatcher`, порог 92%). При близком совпадении в отчёт
   попадает точный фрагмент исходника; повтор LLM нужен только при реальной
   галлюцинации. Изменённые числа и эндпоинты намеренно не «исправляются».
8. `RequirementSetAnalyzer` (Ember, `effort=medium`) получает тот же
   системный префикс с полным документом и ищет дефекты уровня набора:
   нестыковки разделов, противоречия, дубликаты, пропуски, заглушки и
   непокрытые цели. Флаги линтера уровня документа тоже проверяются и
   сливаются с находками модели.
9. Вердикт вычисляется в Python, а не берётся из модели: HIGH/CRITICAL
   находки или FAIL-требования дают BLOCKED, остальные замечания —
   NEEDS_REVISION, иначе READY.
10. CLI сохраняет JSON и формирует Markdown-отчёт с флагами линтера,
    вердиктом и планом первоочередных исправлений.

Промпты лежат в `app/prompts/` и не смешиваются с бизнес-логикой.
`auditor_system.txt` — общий стабильный префикс аудитора, `analyze_batch.txt`
и `set_audit.txt` — только изменяемая задача в конце запроса. Все ответы
модели проходят через Pydantic-модели из `app/models/`.

## Ограничения

- Вердикт детерминирован по severity находок: модель не может «продавить»
  готовый вердикт, но дефекты, которые модель пропустила, вердикт не
  ухудшат.
- Качество результатов зависит от выбранных моделей. Бесплатные модели
  OpenRouter могут быть медленнее, иметь лимиты и хуже соблюдать JSON-схему.
- Полный текст документа передаётся в каждом запросе аудитора (в системном
  префиксе). На очень больших документах запрос может приблизиться к лимиту
  контекста; prefix caching снижает стоимость, но не размер контекста.
- Prefix caching зависит от провайдера: OpenAI-совместимый endpoint может
  игнорировать общий префикс. Приложение гарантирует только байтовую
  стабильность префикса.
- Entity-кластеризация — детерминированная эвристика на словах, эндпоинтах,
  числах и единицах, а не семантические эмбеддинги. Редкие связи без общих
  сущностей могут остаться в разных пакетах.
- Triage может пропустить тонкий дефект, если быстрая модель сочтёт
  требование чистым. Fallback защищает только от сбоя triage, не от его
  ошибки; поэтому флаги линтера и консервативное правило «при сомнении —
  проверять» снижают риск.
- Fuzzy-сверка принимает близкие совпадения (≥92%), но намеренно отвергает
  изменённые числа и эндпоинты. Такая цитата всё ещё требует повтора LLM
  или исключается из отчёта.
- Нет возобновления прерванного прогона и кэширования ответов на диск.
