# AI Requirements Reviewer

ИИ-агент для статической проверки документов с требованиями: извлекает
отдельные требования, проверяет качество каждого из них по критериям
ISO/IEC/IEEE 29148 и IEEE Std 830 и сохраняет структурированные результаты.

Проект для **BCC-HUB x MNU FinTech Hackathon**. Входной документ
организаторов лежит в `documents_organization/requirements.md` (файл не
коммитится — сдаётся отдельно вместе с отчётом).

## Текущий статус

Реализована интеграция с реальной LLM через OpenAI-совместимый API:

- загрузка Markdown и PDF (PyMuPDF, с номерами страниц);
- нарезка документа на чанки с перекрытием и сохранением разделов;
- две модели по этапам: быстрая (`EXTRACTOR_MODEL`) извлекает требования,
  тяжёлая (`AUDITOR_MODEL`) проводит проверки;
- LLM-извлечение требований с валидацией ответа через Pydantic;
- LLM-анализ каждого требования по шести критериям качества;
- проверка всего набора: нестыковки разделов, противоречия, дубликаты,
  пропуски, заглушки и покрытие целей документа;
- детерминированный вердикт READY / NEEDS_REVISION / BLOCKED с планом
  первоочередных исправлений;
- проверка, что evidence — точный фрагмент исходного документа;
- сохранение промежуточных результатов в JSON;
- Markdown-отчёт с нарезкой, находками, аудитом набора и итогом;
- понятные ошибки и ненулевой exit code при недоступности API.

## Установка

Требуется Python 3.11+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Ключ LLM (OpenRouter)

Проект использует пакет `openai` и любой OpenAI-совместимый endpoint.
Для OpenRouter:

1. Зарегистрируйтесь на <https://openrouter.ai/>.
2. Откройте <https://openrouter.ai/keys> и создайте ключ.
3. Скопируйте пример конфигурации и заполните `.env`:

   ```bash
   cp .env.example .env
   ```

   ```dotenv
   LLM_API_KEY=sk-or-v1-ваш-ключ
   LLM_BASE_URL=https://openrouter.ai/api/v1
   LLM_MODEL=anthropic/claude-haiku-5.5
   # Модели по этапам (без них используется LLM_MODEL):
   EXTRACTOR_MODEL=anthropic/claude-haiku-5.5
   AUDITOR_MODEL=meta/muse-ember
   # Режим рассуждений:
   EXTRACTOR_EFFORT=low
   AUDITOR_EFFORT=max
   # Бюджет ответа (reasoning-токены считаются внутри него):
   EXTRACTOR_MAX_TOKENS=4000
   AUDITOR_MAX_TOKENS=16000
   ```

4. Выберите модель в каталоге <https://openrouter.ai/models>. Модель должна
   поддерживать JSON output (`response_format: json_object`); если провайдер
   его не поддерживает, клиент автоматически повторит запрос без этого
   параметра и разберёт JSON безопасным парсером.

### Модели этапов и режим рассуждений

Извлечение идёт моделью `anthropic/claude-haiku-5.5` с
`reasoning.effort = low`. Проверку каждого требования и всего набора ведёт
`meta/muse-ember` с `reasoning.effort = max`. Оба слоуга есть в каталоге
OpenRouter и объявляют параметр `reasoning`.

Обе настройки называются `..._EFFORT` и уходят в одном формате:
`reasoning: {"effort": ..., "exclude": true}` через `extra_body` клиента
`openai`. Поле `exclude` убирает thinking-трейс из ответа, но токены всё
равно тарифицируются как output. Нельзя одновременно слать `reasoning_effort`
и `reasoning.effort` с разными значениями — OpenRouter вернёт 400, поэтому
используется только unified-форма.

Допустимые уровни различаются по моделям и проверяются при загрузке `.env`:

| Модель | Доступные `effort` |
| :--- | :--- |
| `anthropic/claude-haiku-5.5` | `none`, `low`, `medium`, `high`, `xhigh`, `max` |
| `meta/muse-ember` | `minimal`, `low`, `medium`, `high`, `xhigh`, `max` |

`none` для Muse Ember приведёт к 400: модель всегда думает. Настройки и
бюджеты токенов попадают в паспорт прогона. Клиент не отправляет
`temperature` — Haiku 5.5 отвергает любое значение, кроме `1`.

`.env` уже добавлен в `.gitignore`. Ключ никогда не выводится в логах,
отчёте или сообщениях об ошибках.

## Запуск

```bash
python -m app.main analyze \
  --input documents_organization/requirements.md \
  --output reports/report.md
```

Или напрямую через venv:

```bash
.venv/bin/python -m app.main analyze \
  --input documents_organization/requirements.md \
  --output reports/report.md
```

Поддерживаются `.md`, `.markdown` и `.pdf`.

Что появится после успешного прогона:

- `reports/report.md` — отчёт с нарезкой, проверкой каждого требования,
  аудитом всего набора, сводкой и итоговым вердиктом;
- `reports/report.requirements.json` — извлечённые требования, ID, категории,
  исходные ID, местоположение и паспорт прогона (включая коммит агента);
- `reports/report.analysis.json` — находки по каждому требованию, статусы,
  severity, аудит набора и вердикт.

Промежуточные JSON можно отключить флагом `--no-save-json`.

Если ключ не задан, API недоступен, закончилась квота или ответ модели
невалиден, команда печатает понятную ошибку и завершается с кодом `1`.
Фальшивый «успешный» отчёт при этом не создаётся. Если извлечение уже
успело завершиться, его JSON сохраняется для диагностики.

## Как это работает

1. `DocumentLoader` читает Markdown или PDF.
2. `DocumentChunker` режет документ по заголовкам и абзацам на чанки с
   перекрытием, не разрывая строки и сохраняя путь разделов/номер страницы.
3. `RequirementExtractor` отправляет каждый чанк в LLM с промптом
   `app/prompts/extract_requirements.txt`. Модель возвращает JSON, который
   валидируется Pydantic. Дубликаты из перекрывающихся чанков схлопываются,
   внутренние ID `REQ-001…` присваиваются приложением, исходные ID
   (`Ф-1`, `REQ-12`) сохраняются.
4. `RequirementAnalyzer` (модель аудита) анализирует каждое требование
   отдельным запросом. В контекст передаётся весь набор требований — это
   нужно для проверки consistency. Ответ валидируется, а evidence обязан
   быть точным фрагментом исходного текста; иначе анализ отклоняется и
   один раз повторяется.
5. `RequirementSetAnalyzer` (модель аудита) получает полный текст документа
   и весь список требований и ищет дефекты уровня документа: нестыковки
   между разделами, противоречия, дубликаты, пропуски, заглушки и
   непокрытые цели. Каждая цитата evidence сверяется с документом,
   неподтверждённые отбрасываются.
6. Вердикт вычисляется в Python, а не берётся из модели: HIGH/CRITICAL
   находки или FAIL-требования дают BLOCKED, остальные замечания —
   NEEDS_REVISION, иначе READY.
7. CLI сохраняет JSON и формирует Markdown-отчёт с вердиктом и планом
   первоочередных исправлений.

Промпты лежат в `app/prompts/` и не смешиваются с бизнес-логикой.
Все ответы модели проходят через Pydantic-модели из `app/models/analysis.py`.

## Тесты

```bash
python -m pytest
```

или:

```bash
.venv/bin/python -m pytest
```

Тесты не требуют API-ключа и не делают реальных сетевых запросов: ответы
модели и ошибки API замоканы. Покрыты конфигурация (включая модели по
этапам), JSON-парсер, валидация Pydantic, чанкинг, извлечение, анализ
требования, аудит набора и вердикт, проверка evidence и error-path CLI.

## Ограничения

- Аудит набора получает полный текст документа одним запросом; на очень
  больших документах это может упереться в контекст модели аудита.
- Вердикт детерминирован по severity находок: модель не может «продавить»
  готовый вердикт, но дефекты, которые модель пропустила, вердикт не
  ухудшат.
- Качество результатов зависит от выбранных моделей. Бесплатные модели
  OpenRouter могут быть медленнее, иметь лимиты и хуже соблюдать JSON-схему.
- Для consistency в каждый запрос передаётся весь набор требований. На очень
  больших документах это может приблизиться к лимиту контекста модели.
- Строгая проверка evidence требует дословного совпадения; модель может
  получить отказ и повтор, если процитирует текст с искажением.
- Нет возобновления прерванного прогона и кэширования ответов.
